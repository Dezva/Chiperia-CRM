# V1.5: inicio de sesión independiente

Rama: `fix/el-viejo-login-v1.5`, basada en `feat/catalogo-alertas-v1.3-v1.4` (`284b3c449d7600aa76b4646972d49fac0ea99524`).

## Resultado

El sitio conectado muestra únicamente la pantalla de acceso, con la mascota existente de El Viejo, rojo, amarillo y fondo claro. No abre un modal ni muestra el panel o la navegación detrás. El contenedor del CRM comienza `hidden` e `inert` desde el HTML; tampoco aparece si JavaScript está desactivado o tarda en cargar. Mientras se comprueba una sesión se presenta un estado de carga discreto.

El formulario incluye correo, contraseña con mostrar/ocultar, envío con Enter, validación de correo, focos visibles, errores comprensibles y bloqueo de envíos duplicados. No muestra información interna ni errores crudos del proveedor. La contraseña se limpia al completar el intento y al cerrar sesión.

## Autenticación y autorización

Se conserva Supabase Auth, la clave de almacenamiento `viejo-session` en `sessionStorage` y la autorización de la API mediante el integrante validado en `crm_members`.

- Sin sesión, no se solicitan datos de la API ni el catálogo estático de la demo en el sitio conectado.
- Con sesión existente, se consulta la API autorizada antes de revelar el CRM. La comprobación de permisos sigue siendo del backend; ocultar el contenedor no reemplaza esa protección.
- Una sesión próxima a vencer se renueva por `grant_type=refresh_token`. Los pedidos concurrentes comparten esa renovación. Si una solicitud recibe HTTP 401 se renueva y reintenta una vez; si falla, se limpia la sesión y se vuelve al acceso.
- Una cuenta autenticada sin autorización recibe un mensaje para contactar al administrador y no entra al panel.
- Cerrar sesión limpia inmediatamente la sesión local, los datos/editores del CRM y el contenido privado visible. También intenta cerrar la sesión actual en Supabase con `scope=local`; una falla de red no impide el cierre local. Las respuestas tardías no restauran el acceso después de salir.
- Un error de permiso para una operación administrativa mantiene el comportamiento existente; no se interpreta como un cierre de sesión de toda la cuenta.

No se modificaron SQL, migraciones, roles, permisos, credenciales, variables, configuración de Netlify ni reglas comerciales. No se activaron integraciones. Solo se añadió una guarda de limpieza en el componente de avisos para descartar callbacks de un panel ya destruido al terminar la sesión.

Guarnipitan se consultó exclusivamente como referencia, con lectura de `public/index.html`, `public/app.js` y `public/app.css` en una copia temporal del commit `ccd7e9e35ddc70bd51dfaa8b67f6556555480f3c`. Se reutilizó el enfoque de separar `loginScreen` y `shell`, sin copiar sus recursos gráficos ni modificar su repositorio.

## Demo y límites

La demo local sigue abriendo directamente el CRM cuando no hay URL ni clave pública de Supabase. En el sitio conectado no existe botón para entrar en demo, ni se carga ese catálogo antes de iniciar sesión. Si la configuración pública está incompleta, se muestra un acceso no disponible; no se cambia automáticamente a la demo.

No se añade recuperación de contraseña: no hay un flujo de recuperación/redirecciones confirmado para esta instalación. La pantalla solo ofrece iniciar sesión con una cuenta previamente autorizada. No cambia cómo se crean usuarios o se conceden permisos.

Las pruebas de Auth y API usan respuestas simuladas. No se probaron credenciales reales ni se realizaron cambios en Supabase o el sitio publicado. No se validó visualmente Safari/iOS físico; se usó Chromium a 1440 px y 390 px y controles HTML estándar.

## Actualizar el sitio actual mediante GitHub

Esta entrega no cambia la rama publicada ni ejecuta un despliegue de producción. Después de revisar la rama y las capturas:

1. En el sitio **actual de El Viejo** en Netlify, consultar cuál es su rama de producción en la configuración de despliegue continuo. No suponer que sea `main` ni cambiar la rama para hacer esta revisión.
2. Abrir en GitHub una comparación/PR desde `fix/el-viejo-login-v1.5` hacia esa rama únicamente cuando el responsable autorice actualizarla. Revisar la vista previa de Netlify si el sitio la genera. No fusionar hacia `main`, Guarnipitan ni Casa Central para esta tarea.
3. Si la rama publicada sigue en V1.4 (`284b3c4`), la comparación debe contener el login V1.5 y su documentación. Si contiene otros cambios posteriores, revisarlos antes de fusionar; no sustituir archivos a ciegas.
4. Tras la aprobación y fusión en la rama publicada autorizada, Netlify realizará el build configurado. Conservar las variables actuales y el mismo proyecto Supabase. V1.5 no requiere ejecutar migraciones ni modificar credenciales.
5. Comprobar en el dominio publicado: acceso sin sesión, cuenta autorizada, rechazo sin permisos, recarga con sesión y cierre. Un administrador debe probar con cuentas de prueba autorizadas; las pruebas locales de esta entrega no reemplazan esa comprobación.

Si Netlify no genera una vista previa para esta rama, la revisión puede hacerse localmente; no es necesario cambiar su rama de producción para ver las capturas.

Para actualizar la copia de Windows sin tocar la rama publicada:

```powershell
Set-Location D:\chiperia
git status --short
git fetch origin
git switch fix/el-viejo-login-v1.5
git pull --ff-only origin fix/el-viejo-login-v1.5
pnpm install --frozen-lockfile
pnpm build
pnpm dev
```

Conservar primero cualquier cambio local pendiente. `pnpm dev` sirve la demo estática si no se han definido las credenciales públicas; no sirve las Functions. No copiar claves secretas en el navegador ni en Git para probar el acceso.
