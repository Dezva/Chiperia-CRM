# V1.7 — Delivery, pedidos y resumen financiero

Desarrollo y publicación en `fix/el-viejo-login-v1.5`, desde `2fae69aca44d38e7b19a30e5fd80fe06c9661a32`. Se conserva V1.5, V1.6 y la persistencia de ubicaciones de V1.6.1. No se crearon ramas, categorías ni modalidades de pedidos de prueba. Los datos ficticios pertenecen exclusivamente a pruebas y demo local.

## Delivery sin referencia obligatoria

El requisito anterior estaba duplicado en el motor del bot y en las funciones SQL de registro y aceptación. Ahora únicamente se exige un punto válido de WhatsApp, asociado a la conversación/pedido. Una dirección escrita no sustituye ese punto. Las coordenadas siguen validadas en el webhook y mediante restricciones de PostgreSQL. Google Maps continúa disponible para el empleado.

El cliente puede confirmar sin describir su casa. «No tengo referencia», «No hay ninguna referencia a proporcionar», «No te voy a dar otra referencia», «Ya te envié mi ubicación», «¿Recibiste mi ubicación?» y «¿Qué falta para mi pedido?» no alteran productos ni cantidades. Las aclaraciones se resuelven sin IA. Las referencias voluntarias se conservan como información adicional, incluso si llegaron antes del punto. No se inventan calles a partir de coordenadas.

La recepción del punto invita a escribir CONFIRMAR PEDIDO cuando hay productos. Solo `guarni_finish`, después de insertar y relacionar el pedido dentro de su transacción, encola el mensaje de solicitud registrada. El pedido sigue pendiente de aceptación del negocio. El empleado debe revisar el punto, introducir explícitamente el costo de envío (cero es válido), revisar disponibilidad/importes y aceptar. Para buffet sigue siendo obligatorio tomar la conversación y acordar un importe humano; el bot no anuncia el importe de buffet.

Se conservan la reserva del worker, deduplicación, descarte de ubicaciones antiguas, asociaciones del pedido, cambio de punto, revisión de puntos nuevos durante el reparto, cambio de servicio, retiro sin ubicación y limpieza del punto al terminar un borrador. Repetir «quiero dos» mantiene dos; un incremento explícito suma. Las consultas posteriores sobre la ubicación de una solicitud registrada no vuelven a pedir confirmar otro pedido.

## Interfaz de pedidos

`public/order-detail.js` presenta estado, cliente, servicio, fecha de Paraguay, productos, importes, entrega o retiro, responsable registrado, método de pago, estado de pago y línea de tiempo. Los iconos nuevos son SVG locales; no requieren servicios ni bibliotecas. Los formularios no piden IDs ni JSON. En móvil, los listados de pedidos se presentan como tarjetas con acceso visible al detalle.

Las acciones principales dependen del estado guardado. Se ofrecen aceptación/rechazo, preparación, listo, reparto cuando corresponde y entrega/retiro. La cancelación aparece en Otras acciones. Las opciones administrativas están separadas. SQL conserva la validación de transiciones, precios, disponibilidad y aceptación humana. La interfaz envía la versión revisada del pedido; PostgreSQL rechaza guardar una versión anterior tras un cambio concurrente.

El detalle consulta su pedido e historial actuales al abrirse, incluyendo pedidos abiertos desde las alertas. No depende del historial general limitado del resumen. Las fechas y etiquetas de la línea de tiempo usan `shared/order-presentation.js`. Solo se muestra un empleado cuando existe un actor/responsable registrado. Un pedido histórico sin fecha comprobable de entrega lo indica expresamente.

Retiro muestra «Retiro en el local», sin una referencia pendiente. Delivery sin referencia muestra «Sin referencia adicional». Método de pago y estado de pago se muestran por separado. Gestionar pago permite completar el método incluso en un pedido finalizado y advierte de pagos históricos recibidos sin método.

## Cobros y reembolsos

`viejo_payment_movements` guarda un movimiento de recepción y, si corresponde, uno de reembolso completo por pedido. Cada movimiento conserva importe, método al registrarlo, fecha real de registro, servicio, actor e identificador/número del pedido. No copia cliente, teléfono, dirección, coordenadas ni productos. La unicidad por pedido/tipo y el bloqueo del pedido evitan duplicar un cobro al repetir Guardar.

Seleccionar un método con estado Pendiente no registra dinero recibido. Para marcar Recibido se exige método configurado e importe final confirmado. Un pedido pagado puede seguir en preparación; uno entregado puede seguir sin cobrar. Marcar entrega no registra cobro ni viceversa.

El flujo es Pendiente → Recibido → Reembolsado; las repeticiones del mismo estado son idempotentes. No se vuelve de Recibido a Pendiente para ocultar una recepción. Un reembolso registra una devolución efectivamente realizada; no mueve dinero ni llama a un proveedor. V1.7 contempla un pago y una devolución completos, sin cobros parciales ni nuevos ciclos de cobro sobre el mismo pedido reembolsado. Corregir el método visible deja historial y no genera otro movimiento monetario.

## Resumen por período

`public/financial-summary.js` consulta `viejo_financial_summary` a través de una API autenticada. Los agregados se calculan en PostgreSQL sobre todos los pedidos/movimientos, sin limitarse a las 500 filas del listado. La demo calcula las mismas clases de datos locales y no pretende ser una conexión real.

El período inicial es Este mes. Hay Hoy, Esta semana (lunes a domingo), Este mes, Mes anterior, Rango personalizado inclusivo y Todo el historial. El filtro general permite ambos servicios, Buffet o Chipería. Los límites son días de `America/Asuncion`, con inicio inclusivo y siguiente día exclusivo en SQL. El cambio de mes se refleja al actualizar; no hay reinicio ni borrado de contadores.

- Pendientes de revisión y pedidos activos muestran la situación **actual**, como indica su texto.
- Pedidos completados e importe de pedidos completados usan `completed_at` dentro del período.
- Cobros y reembolsos usan la fecha de sus propios movimientos, independientemente de la entrega.
- Cobro neto registrado = cobros registrados − reembolsos registrados. No representa ganancias ni incorpora costos operativos.

Las solicitudes relacionadas mantienen importes separados. Al aceptar dos deliveries del mismo grupo al mismo punto, SQL impide introducir dos costos positivos: el empleado debe dejar cero en el segundo si comparten la entrega. No se descuentan arbitrariamente cobros históricos ni se cambian totales ya acordados. Los grupos históricos que ya tuvieran cargos duplicados requieren revisión comercial; la instalación no los recotiza.

## Compatibilidad histórica

La instalación no borra pedidos, cambia productos ni restaura precios. Añade `accepted_at`, `completed_at`, `cancelled_at`, `rejected_at` y `version` a los pedidos. Un trigger registra fechas en nuevas transiciones e incrementa la versión en cada actualización.

Para pedidos existentes, solo se recuperan fechas de eventos donde las instantáneas de `viejo_history` prueban una transición real. No se usa `created_at` o `updated_at` como fecha de entrega/pago. Los cobros históricos solo se importan cuando un evento de pago identifica cambio de estado e importe final positivo; las actualizaciones repetidas sin cambio no suman de nuevo. Los identificadores de pedido, carritos, precios del catálogo y asociaciones se mantienen.

El resumen avisa de pedidos completados sin fecha, importes finales desconocidos y pagos sin recepción fechada. Un pedido completado sin fecha no se asigna a un día/mes; sí puede contarse en Todo el historial. Un pago sin fecha/importe suficiente no se suma como recepción fechada ni se inventa un movimiento al corregir su método. Un reembolso de un pago histórico incompleto puede quedar en un período distinto de la recepción conocida: el neto representa únicamente movimientos registrados, con la limitación histórica indicada.

## Eliminación administrativa de pedidos

Opciones administrativas → Eliminar pedido está disponible únicamente para administradores. API y SQL vuelven a verificar el rol. La vista previa incluye pedido, cliente, servicio, fecha, estado, importe y estado de pago. Exige escribir ELIMINAR y presentar la huella de esa misma vista previa. Si cambió el pedido, se debe revisar otra vista previa.

Solo se eliminan estados terminales: Entregado/retirado, Rechazado o Cancelado. Se bloquean pedidos activos, procesamiento y envíos pendientes/inciertos de la conversación. Si el pedido tiene un pago o movimientos, exige además reconocer la conciliación y conservación de esa evidencia. La vía SQL antigua `guarni_delete` no permite evitar esta confirmación.

Se elimina el pedido y su historial de detalle por sus relaciones existentes. Se conservan cliente, conversación, otros pedidos, mensajes y ubicaciones de origen. Los webhooks originales siguen deduplicados; una limpieza posterior sigue usando las protecciones de V1.6. No se genera un mensaje de cancelación.

Los movimientos monetarios sobreviven con `order_id = null`, conservando referencia estable del pedido, importe, fecha y servicio. Se conserva auditoría mínima de actor, operación, estado anterior, importe, estado de pago y resultado, sin copiar información personal. Por ello baja el importe de pedidos completados, mientras los cobros/reembolsos reales conservados siguen en el resumen con un aviso de conciliación. Eliminar no simula una devolución ni reemplaza registrar un reembolso.

La eliminación de clientes de V1.6 también conserva estos movimientos mediante la misma clave foránea con SET NULL; su confirmación de pedidos históricos sigue siendo obligatoria.

## Actualizar Supabase: 015 → 016 → 017

La base independiente de El Viejo puede estar en 015. Antes del despliegue manual:

1. Conservar una copia de seguridad y verificar la base de El Viejo que se va a actualizar.
2. Si 016 aún no está aplicada, ejecutar **completo `database/016_referencia_delivery.sql`** en el SQL Editor de esa base. Si ya está aplicada, no hace falta repetirla.
3. Ejecutar **completo `database/017_delivery_y_pedidos_v17.sql`**, después de 016.
4. Comprobar las funciones, columnas y registro de movimientos antes de desplegar el código.

No volver a ejecutar 005, 007, 009, 010, 011, 012 o 015 para actualizar una base que ya está en 015: podrían restaurar funciones previas. 017 conserva las correcciones de persistencia de 016 y elimina el requisito de referencia en las funciones vigentes. Ambas migraciones tienen transacción; 017 es reejecutable sin duplicar movimientos históricos.

017 modifica `guarni_orders`, crea `viejo_payment_movements`, índices y el trigger de fechas/versiones. Reemplaza `guarni_process_location`, `guarni_finish`, el núcleo privado `viejo_staff_v12_base` y la entrada `viejo_staff`, conservando los wrappers de catálogo/configuración. Crea `viejo_financial_summary` y `viejo_delete_order`, y cierra el atajo antiguo de borrado mediante `guarni_delete`. Los helpers privados no se conceden a usuarios ni al rol de API; las entradas de backend solo a `service_role`. No se cambian RLS existentes ni configuraciones comerciales.

Verificaciones de lectura en SQL Editor:

```sql
select to_regprocedure('public.viejo_financial_summary(uuid,text,date,date,text)'),
       to_regprocedure('public.viejo_delete_order(uuid,uuid,boolean,text,text,boolean)'),

```

Si una migración falla, conservar el error, ejecutar ROLLBACK si la sesión sigue en una transacción fallida y corregir la causa antes de ejecutar nuevamente el archivo completo. No continuar con un SQL parcial ni volver a migraciones antiguas. No desplegar el código nuevo hasta que 017 esté aplicada. Si ya se desplegó y falta la RPC, la API informa la migración pendiente para resumen/eliminación.

## Un único despliegue manual de Netlify

Después de aplicar el SQL, revisar los cambios de esta misma rama y realizar **un despliegue manual** del commit final. Mantener las variables y credenciales actuales. No recrear el sitio, cambiar webhooks ni habilitar proveedores nuevos. Si el sitio tiene despliegues automáticos al hacer push, su responsable debe controlar esa automatización para respetar este orden; este trabajo no cambia configuración de Netlify ni llama a su API de despliegue.

Para actualizar la copia Windows que ya está en la rama requerida, primero conservar cambios locales:

```powershell
Set-Location D:\chiperia
git status --short
git pull --ff-only origin fix/el-viejo-login-v1.5
pnpm install --frozen-lockfile
pnpm build
```

Estos comandos no aplican SQL ni despliegan Netlify. Para explorar la demo: `pnpm dev`.
