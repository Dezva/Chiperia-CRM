# Actualización V1.1 sin perder datos

Base auditada: `a0bb1a23fc89637d2cf12748b227538b7f41e1c8`. Rama de revisión: `fix/el-viejo-v1.1`. No se modifica main ni Guarnipitan, ni se publica el entorno cloud o producción.

## Hallazgos y cambios

1. CI fija `ubuntu-24.04`, conservando Node 24, pnpm 11.25.0, lockfile y Playwright 1.58.2. Chromium se instala con el comando del paquete fijado y `CHROMIUM_PATH` se obtiene de `chromium.executablePath()`. Todas las suites siguen habilitadas.
2. `guarni_finish` usa un booleano `submitted` independiente del paso a atención humana. Registra pedido + asociación y limpia el borrador en la misma transacción. Conserva la ubicación histórica y la deduplicación por trabajo/mensaje. Retiro, cancelación, cambio de servicio y release limpian referencias temporales.
3. `menu_editor` permite al encargado editar, reconocer y publicar menús. Se comprueba en interfaz, API, endpoints de fotos/visión y RPC. Solo administradores asignan/revocan permisos; no habilita ajustes, usuarios ni catálogo.
4. Worker consulta por mensaje el menú publicado del día de Asunción, solo metadatos/platos; no descarga imágenes. Se añade `service` al SELECT de catálogo, imprescindible para chipería.
5. Se reemplaza la comparación de objetos JSON por campos de productos, independiente del orden de claves de JSONB. Esto evita recotizaciones interminables al recuperar carritos desde PostgreSQL.
6. Visión valida estado completado, JSON, campos/tipos/límites y rechazos; descarta truncamientos. Timeout 45 s, errores sanitizados, caché por imagen/proveedor/modelo/versión de esquema, escritura idempotente concurrente y consumo reportado por el proveedor. Nunca publica propuestas.
7. API general devuelve metadatos de imágenes, no Base64. Lectura de original autenticada por demanda. Storage privado opcional para nuevas fotos; originales históricos conservados. Pedidos relacionados muestran enlaces a sus solicitudes e importes independientes; no se añade automáticamente ningún delivery.

## Instalación existente

Estos pasos son para una futura actualización autorizada del despliegue independiente. **No se ejecutaron contra Supabase alojado ni producción.**

1. Hacer copia de seguridad de la base y de cualquier Storage existente; comprobar conteos de menús, pedidos y ubicaciones en un clon aislado. Mantener `BOT_ENABLED=false`, `WHATSAPP_SEND_ENABLED=false`, `AI_IMAGE_ENABLED=false` mientras se valida. No utilizar proyectos ni credenciales de Guarnipitan.
2. Aplicar **solo** `database/009_v11_fiabilidad.sql`, después de que 001–008 ya estén instaladas según la guía original. No reejecutar 001/002/006/007 para actualizar funciones: podrían restaurar versiones antiguas. 009 es transaccional, aditiva y reejecutable; no borra registros. Añadir la columna generada de metadatos puede bloquear/revisar la tabla de menús durante la migración: programar una ventana acorde al tamaño de la base.
3. Desplegar el backend y frontend de la misma rama después de la migración. Las nuevas Functions necesitan las nuevas columnas de permisos y fotos. Refrescar la sesión/página para cargar permisos actuales. No habilitar integraciones automáticamente.
4. En Usuarios, un administrador concede `menu_editor` al encargado, manteniendo rol `member`. Probar con administrador, encargado con permiso, empleado sin permiso y usuario ajeno. La revocación se vuelve efectiva en la siguiente petición: no se confía en el permiso guardado en el navegador.
5. Verificar un buffet delivery A, toma humana y reactivación, segundo delivery B, estado independiente de cada pedido y ausencia de ubicación residual. Repetir con chipería. Para procesos antiguos pendientes de antes de la actualización, completar la atención y reactivar explícitamente: release limpia su borrador sin eliminar el pedido.
6. Publicar menú A y actualizar B en la misma conversación. Verificar agotados y ausencia del menú anterior como oferta vigente. Confirmar que los cálculos de chipería y los importes humanos del buffet permanecen intactos.
7. Si se decide revertir solo la aplicación, conservar las columnas y datos nuevos; no ejecutar DROP ni borrar migraciones/datos. Volver al código antiguo reintroduciría los defectos de worker/JSON, por lo que requiere evaluación separada.

Para una instalación nueva aplicar 001,002,005,006,007,008 y finalmente 009. 003 es reservado y 004 autoriza la primera cuenta como en V1.

## Fotos privadas: preparación opcional

1. En un proyecto Supabase **aislado y autorizado**, aplicar `database/storage/001_menu_private_bucket.sql`. Usa `el-viejo-menu-private`, límite 3 MB y PNG/JPEG/WebP. Se niega a continuar si un bucket con ese nombre es público. No crea políticas públicas ni de acceso directo de anon/authenticated.
2. Auditar políticas generales existentes de `storage.objects`: no deben conceder acceso a este bucket a visitantes ni usuarios sin autorización. La aplicación accede exclusivamente mediante Functions autenticadas y clave de servidor. Esta auditoría y la compatibilidad de la clave con Storage alojado requieren prueba real posterior; los tests locales usan un servidor simulado.
3. Configurar `MENU_PHOTO_STORAGE_ENABLED=true` y, si cambia, `MENU_PHOTO_BUCKET`, solo en ese entorno. El backend verifica que el bucket declare `public=false` antes de transferir archivos. No usa URLs públicas permanentes ni enlaces firmados enviados por el API general.
4. Subir una imagen desde el CRM. El archivo se identifica por SHA-256; `viejo_menu_photos` guarda metadatos/ruta y `viejo_menus.photo_id` referencia esa foto. Reintentar una subida idéntica reutiliza el archivo/registro. La foto solo se descarga bajo una petición autenticada y se verifica contra el hash. El navegador usa una URL Blob efímera para mostrarla.
5. `MENU_PHOTO_RETENTION_DAYS` vacío conserva sin vencimiento. Un número positivo registra `expires_at` como fecha de revisión de conservación. **No se borran automáticamente imágenes históricas**: antes de implementar eliminación programada, el negocio debe decidir conservación y auditar referencias/versiones. Si se sube un objeto pero falla la inserción de metadatos, puede quedar un objeto huérfano recuperable; revisar por hash antes de cualquier limpieza.
6. Las fotos Base64 anteriores permanecen intactas en `viejo_menus.image`. El API general deja de devolverlas; se recuperan bajo demanda por `menu-photo`. Al clonar/actualizar un menú, `source_menu_id` conserva su original. No se realizó una conversión masiva ni se borró Base64 histórico. Esa migración se hará por lotes, con comparación de hashes y copias de seguridad, después de validar infraestructura real.

Con Storage apagado, se mantiene la escritura compatible de imágenes en la base. La demo usa almacenamiento local del navegador y transcripción manual; no depende de Supabase Storage ni de IA externa. La cuota del navegador y el volumen de fotos siguen limitando ese modo.
